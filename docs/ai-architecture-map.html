AI-native development system · responsibilities map

Who does what — and where each piece lives

The confusion is almost always one thing: what is neutral (runs on any brain) versus what belongs to the adapter (specific to the AI tool). These two drawings separate that.

01The boundary: neutral core ↔ adapter

The golden rule (Principles IV & V): knowledge lives in git and the mechanism is neutral; the AI brain is a swappable plug. Switching AI = regenerating an adapter, never rewriting the project.

  • neutral flow
  • crosses the boundary (observability)
  • boundary / human gate
This is why fine-tuning and runtime observability (tokens, traces, logs, evals) were decided as adapter-scoped (ADR-0012): they are tool-specific. The core only ever receives the summary, in git.

02The loop — and where a run's metrics come from

The same SDD loop, showing the point that trips people up: the agent and the harness do not commit. A session's numbers wait in a sidecar inside .git/ until the next commit, and the hook stamps them (then deletes the sidecar → one session = one commit).

03Responsibilities table

Who owns what — and who sees tokens. Note: only the adapter sees tokens; the harness measures health; the hook records; the human decides the gates.

In one sentence. The core (git + harness + hook + metrics) is neutral and holds the truth and the mechanism; the adapter is the swappable brain that thinks and sees tokens; the human holds the four gates. The project's lever is context in git — not model weights, not provider telemetry.

04Decisions (decisions/): the rules you build within

Architecture is decided once, not re-decided per feature. Each ADR is recorded once, becomes immutable in git, and binds all future work. Features don't re-argue architecture — they inherit it at planning time. A task that would break an ADR is not a judgment call: it stops and escalates (the architecture-change human gate).

How decisions connect to the rest of the map. The ADRs are the rules the neutral core (diagram 01) enforces and the loop (diagram 02) obeys: tasks.md names them, the harness runs within them, and any conflict routes to a human gate. That's how "architecture decided, not re-decided" stays true across every spec.

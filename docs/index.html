ai-native / android · case study
a development architecture, not a tool

Specs are the source of truth. Humans hold the gates. The AI runs the loop.

The differentiator in software is shifting from who writes the code to who maintains a legible, verifiable system of intent that both people and models can act on safely. This is one concrete, opinionated answer — proven on a real, multi-module Android codebase.

Why it survives a tool swap

Neutral core, pluggable brain

The project's intelligence lives in tool-agnostic files in git. The AI tooling is a thin, replaceable adapter on top. Swapping the model means rewriting an adapter — never the project.

Try it — the loop in four commands

How you create a new spec

A person authors the intent and approves each artifact (human-paced); an agent then works the approved list to green (ai-paced). Every feature travels the same four steps — architecture is inherited from the ADRs, never re-decided.

1 · human
/speckit-specify "Users can <do X>: <behavior>"
Creates specs/<NNN>/spec.md and a branch — user stories, acceptance scenarios, success criteria. Behavior only, no implementation detail.
2 · human
/speckit-plan
Design + contracts, with the architecture pulled from the ADRs. A Constitution-Check gate resolves any open question here.
3 · human
/speckit-tasks
A dependency-ordered, test-first checklist grouped by user story — this approved tasks.md is the handoff to the agent.
4 · agent
/speckit-implement  — or hand the tasks to a local LLM via opencode
Works the list one task at a time, verifying each until green. You review and merge — the human gate. (This is exactly how spec 004 shipped.)
